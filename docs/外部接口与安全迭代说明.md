# 外部接口与安全迭代说明

本文档说明本轮新增的禁忌管理、营养素推荐排序、病例识别兜底和外部接口能力。所有改动遵循既有安全原则：产品目录、禁忌规则、医生规则和人工审核优先，系统不得因为 RAG 或外部接口绕过安全边界。

## 1. 产品禁忌与慎用提示

新增数据文件：

- `backend/app/data/product_safety_matrix.json`

该文件由药企提供的《产品服用禁忌汇总》整理生成，原始 DOCX 不进入 Git。运行时会把安全矩阵覆盖到产品目录中，补充以下信息：

- `contraindications`：明确禁用或禁忌场景。
- `cautions`：慎用场景，可推荐但必须提示顾问或医生确认。
- `interaction_warnings`：药物、手术、特殊人群等交互风险。
- `exclusion_rules`：用于自动排除的结构化规则。

处理原则：

- 出现明确“禁用、禁忌、避免使用”等表达时，作为自动排除规则。
- 出现“慎用、需监测、需确认”等表达时，不直接排除，但进入推荐草案和报告提示。
- 产品目录中不存在或未启用的条目不会被新增为可推荐产品。

## 2. 产品标签矩阵排序优化

本轮对产品标签矩阵的排序权重做了更细分的处理：

- 症状命中：优先级最高，用于把与当前主诉直接相关的营养素排在前面。
- 既往病史/问题命中：用于识别甲状腺、血糖、血脂、胃肠、炎症等明确问题。
- 健康目标命中：用于配合“控糖、睡眠、免疫、代谢”等目标。
- 生活方式命中：作为辅助因素，避免只因泛化描述把弱相关产品提前。

推荐草案中的 `evidence_details` 会显示类似“产品标签命中：症状”的证据标签，方便内部审核。客户可见报告仍只展示经过整理后的推荐理由，不展示内部打分。

## 3. 病例识别兜底

为减少新增医院模板导致的漏识别，本轮增加两类防线：

1. 单位归一化增强
   - 支持 `10 9/L`、`10*9/L`、`10×9/L`、`10^9 / L` 等形式统一为 `10^9/L`。
   - 支持 `μmol/L`、`µmol/L`、部分 OCR 误识别字符统一为 `umol/L`。

2. 疑似未识别指标池
   - 对“像检验指标但未被字典识别”的行，加入人工校对提示。
   - 示例：`疑似未识别指标：载脂蛋白E 1.82 g/L ↑ 0.20-1.20`
   - 该机制不会把未知指标强行归一化，也不会直接参与推荐，只用于提醒人工审核。

## 4. 外部接口

外部接口统一挂载在 `/api/v1` 下，使用 Bearer token。医生账号由外部系统管理，工作台不接收医生用户名/密码；外部系统通过系统间共享密钥签名声明医生身份，工作台验证签名后签发短期 Bearer session。

服务端需配置：

```text
FM_EXTERNAL_TRUST_SHARED_SECRET=由双方线下约定的高强度共享密钥
```

### 4.1 外部系统签名换取 Token

`POST /api/v1/auth/token`

签名串按以下顺序用换行符拼接：

```text
issuer
doctor_id
doctor_name
timestamp
nonce
```

签名算法：

```text
HMAC-SHA256(secret, canonical_payload).hexdigest()
```

允许 `signature` 使用纯 hex 字符串，也允许使用 `sha256=<hex>` 格式。`timestamp` 与工作台服务器时间偏差超过 300 秒时会拒绝。

请求：

```json
{
  "issuer": "customer-system",
  "doctor_id": "doctor-001",
  "doctor_name": "外部医生A",
  "timestamp": 1760000000,
  "nonce": "random-nonce-至少8位",
  "signature": "hex_hmac_sha256_signature"
}
```

响应：

```json
{
  "access_token": "sess_xxx",
  "token_type": "bearer",
  "expires_in_days": 14,
  "doctor_id": "doctor_ext_xxx",
  "display_name": "外部医生A"
}
```

后续接口需携带：

```http
Authorization: Bearer sess_xxx
```

### 4.2 创建病例

`POST /api/v1/cases`

请求：

```json
{
  "customer_name": "客户姓名",
  "consultant_id": "顾问姓名",
  "notes": "可选备注",
  "analysis_mode": "llm_primary"
}
```

说明：

- 外部接口创建的病例默认进入医生私有工作区。
- 只有创建该病例的医生 token 可以继续上传附件、生成推荐或获取报告。

### 4.3 上传病例或问卷附件

`POST /api/v1/cases/{case_id}/attachments`

表单字段：

- `files`：一个或多个附件。
- `attachment_type`：`case` 或 `questionnaire`。

返回：

```json
{
  "case_id": "case_xxx",
  "status": "parsing_completed",
  "results": [
    {
      "file_id": "file_xxx",
      "filename": "labs.txt",
      "attachment_type": "case",
      "status": "parsed",
      "lab_item_count": 2,
      "parse_warnings": []
    }
  ]
}
```

说明：

- `case` 附件会进入 OCR/文本抽取和指标识别流程。
- `questionnaire` 附件会进入问卷识别流程。
- 若出现疑似未识别指标，会写入 `parse_warnings`，供人工校对。

### 4.4 读取与保存解析校对

```http
GET /api/v1/cases/{case_id}/parsing-review
PUT /api/v1/cases/{case_id}/parsing-review
Authorization: Bearer <token>
```

支持读取和保存普通实验室指标、附件校对状态以及慢性食物敏感、肠道功能健康评估、肠道菌群三类专用报告。保存时必须提交 `expected_revision`；版本过期返回 `409 parsing_revision_conflict`。

只有人工校对完成的专用报告才能进入草案分析。外部客户端不能新增自动解析中不存在的专用报告 ID、修改报告类型或增删肠道指标代码。详细字段和安全约束见 `docs/肠道报告识别与外部编辑接口.md`。

### 4.5 生成营养素推荐 JSON

`POST /api/v1/cases/{case_id}/nutrition-recommendations`

返回：

```json
{
  "case_id": "case_xxx",
  "draft_id": "draft_xxx",
  "status": "pending_review",
  "manual_review_required": true,
  "confidence": 0.78,
  "recommendations": [
    {
      "sku_id": "sku_xxx",
      "name": "产品名称",
      "category": "营养素类别",
      "dosage": "每日 1 粒，随餐使用。",
      "reason": "推荐理由",
      "warnings": ["慎用或交互提示"]
    }
  ],
  "contraindications": [],
  "missing_info": []
}
```

说明：

- 该接口只生成草案，不自动发布客户报告。
- 草案仍需人工审核。
- 明确禁用产品会被排除，慎用产品可保留但必须带提示。

### 4.6 获取最新营养素推荐

`GET /api/v1/cases/{case_id}/nutrition-recommendations/latest`

用于外部系统拉取当前病例最近一次推荐草案。

### 4.7 读取与修改待审营养素草案

```http
GET /api/v1/drafts/{draft_id}/nutrition-recommendations
PATCH /api/v1/drafts/{draft_id}/nutrition-recommendations
Authorization: Bearer <token>
```

医生可以调整顺序、删除产品、添加已启用目录产品以及修改剂量和理由。PATCH 必须提交 `expected_revision`；服务端会重新执行产品目录、禁忌和病例安全校验。客户端不能删除或覆盖安全警告、禁忌和证据字段，已发布草案不能修改。

### 4.8 获取处方信息

`GET /api/v1/drafts/{draft_id}/prescription-items`

基于已生成推荐草案返回草案级总医嘱说明，不改变 `nutrition-recommendations` 既有响应。

响应：

```json
{
  "case_id": "case_xxx",
  "draft_id": "draft_xxx",
  "status": "pending_review",
  "medical_advice": "处方级营养素用于补充身体当下所需营养，予以肝脏解毒代谢支持、免疫调节支持等方向的营养支持，帮助平衡免疫、抗炎、抗氧化及代谢调节。",
  "advice_source": "local_fallback"
}
```

说明：

- `medical_advice` 是整张营养素方案的总医嘱说明，长度约 50-100 字。
- 文案基于推荐理由、异常指标和功能医学系统失衡分析生成；LLM 可用时润色，不可用或调用失败时使用本地兜底文案。
- 文案采用“对症支持 / 营养支持 / 营养干预”表达，不使用“治疗、治愈、疗效”等疾病治疗承诺。
- `advice_source` 为 `llm` 或 `local_fallback`。
- 最终审核报告和 PDF 会在“首月营养素干预方案”之后展示“总医嘱说明”。
- 输出会清理内部证据、关联度、RAG、产品标签命中、后台判断、本地路径等非交付话术。
- 该接口仍受医生私有工作区隔离保护，只有病例所属医生 token 可以访问。

### 4.9 获取报告下载地址

`GET /api/v1/drafts/{draft_id}/report-download`

说明：

- 仅已审核发布的草案可返回下载地址。
- 未审核草案返回 `409 Report is not approved yet`。

响应：

```json
{
  "draft_id": "draft_xxx",
  "filename": "客户报告.pdf",
  "download_url": "http://localhost:8000/api/v1/drafts/draft_xxx/report.pdf"
}
```

PDF 下载：

`GET /api/v1/drafts/{draft_id}/report.pdf`

同样需要 Bearer token，且只允许病例所属医生访问。
