# “核心结论与健康画像”三层规则改造计划

## 1. 基线与范围

- 规则来源：根目录 `核心结论与健康画像_三层规则.md`。
- 目标基线：本地跟踪分支 `codex/current-supplement-overlap`，对应 PR #31 head `2ecc4b5`（父提交 `875c1ae`）。PR #31 主要增加“当前营养素/补充剂重复服用提醒”，不直接修改第一节生成逻辑；本改造应在该分支之上开发，避免丢失首月负荷校验所需的当前补充剂数据。
- 本期主范围：客户报告第一节“核心结论与健康画像”的判读、决策、写作和强制校验；同步调整最终审核重渲染、PDF/外部报告一致性和自动化测试。
- 本期不把产品召回分数直接改造成枢纽分数，也不允许 RAG 或大模型自由创造机制链。

## 2. 当前实现与规则的主要差距

1. `build_core_health_portrait()` 当前从 `StructuredSystemFinding` 按证据等级、系统优先级和分数排序，首项直接成为“核心干预枢纽”。这仍属于“严重/高分者优先”，没有执行枢纽四判据。
2. 当前“主线”是身体系统或发现名称的串联，不是通过“生理通路、方向合理、至少两项客观指标同向支持”校验后的机制链。
3. 现有上限是 5 条主线，与规则要求的 1–3 条不符；现有测试也固化了“五条主线”的旧行为。
4. 数据模型只有系统优先级与总分，缺少 T1/T2、临床决策线、趋势、证据模态、可干预性、上下游位置、收益面和轴归属。
5. 红旗目前只改变文案为“优先医学评估”，没有从靶点候选中强制排除；结节、占位、先天变异、陈旧改变等也可能被选为第一主线或干预核心。
6. 第三句只给出一条泛化生活方式方向，没有 3–6 步依赖有序的干预闭环，也没有落到主链实际对应的功能医学轴。
7. 最终审核阶段会重新构造第一节，但没有传入最终 `abnormal_findings`，可能丢失数值、单位、趋势和器质性证据，造成草案与最终报告不一致。
8. RAG 融合仍允许修改第一节，随后又被本地逻辑覆盖；既浪费调用，也可能在其他路径产生不合规文本。

### 2.1 与现有业务规则的兼容处理

以下不是简单删除旧逻辑，而是需要分层兼容：

1. **系统优先级与枢纽优先级分离**：现有证据分数继续服务“功能医学系统失衡分析”和产品覆盖，不再直接决定第一节枢纽。严重度可作为同资格候选的次级排序项，但不能取代上游位置、可干预性和收益面。
2. **`red_flags` 不能直接等同 P0**：当前列表同时包含真正医学红旗、孕哺/未成年、用药相互作用和“需重点审核”提示。必须新增结构化风险等级，将 `P0_referral` 与 `review_required`、`dose_caution` 分开；只有 P0 强制退出营养靶点。
3. **慢性食物敏感不应全量丢弃**：保留“食物敏感不能单独形成第一节主线”的既有约束；但若属于医生确认的客观结果，且与注册表中的肠道/免疫机制链满足方向和聚集条件，可作为辅助证据。是否允许进入第一句的器质性损害信号需由医学团队单独确认，默认不进入。
4. **证据等级需要拆模态**：当前第一节把 `clinical_confirmed` 排在 `lab_abnormal` 前，且 `clinical_confirmed` 混合影像、病理、既往诊断。新增报告专用证据模态后，严格执行客观检验 > 影像/病理 > 症状群 > 自述；不直接改变产品安全模块已有的证据枚举含义。
5. **产品与剂量规则保持权威**：三层算法只决定第一节的主链、靶点和闭环表达，不绕过既有产品召回、安全矩阵、剂量计算和医生审核。闭环步骤必须反向校验已生成方案是否承接。
6. **当前补充剂属于负荷输入，不属于画像事实**：PR #31 的当前补充剂结构用于重复核对和首月负荷降级，医生端提示不得进入客户第一节。
7. **人工报告不可绕过校验**：现有审核流程会重建第一节，这一点与“任一校验不通过即打回”方向一致；改造后应基于决策对象和输入哈希重建，而不是恢复自由文本直接发布。
8. **冲突优先级明确**：仅就“核心结论与健康画像”的判读、靶点决策、三句写作和强制校验而言，三层文档优先于旧实现、旧提示词和旧测试；产品召回、剂量、安全矩阵、医生审核与客户隐私规则继续保持独立权威。

### 2.2 当前质量基线

- `main` 已 fast-forward 到远端 `875c1ae`，无已跟踪文件冲突；PR #31 head `2ecc4b5` 是 `main` 的直接后继，尚未合并。
- 前端 `npm run build` 通过。
- 后端全量测试结果为 `260 passed, 17 failed, 221 subtests passed`。其中 2 项为当前环境缺少可用 FAISS 稠密索引；其余失败主要集中在新收尾章节、章节编号、风险提示和旧测试预期未同步。实施本改造前应先建立“已知失败清单”，避免把存量失败误归因于三层规则改造。
- 第一节专用测试 `test_report_content.py` 当前通过，但包含“五条主线”等与新规则冲突的旧断言，因此“测试通过”不代表符合三层规则。

## 3. 目标数据结构

建议新增独立模块 `backend/app/services/health_portrait.py`，把“临床推理产物”和“面向患者的三句话”分离。`report_content.py` 只保留渲染兼容入口。

### 3.1 判读层对象

`GradedFinding`

- `finding_id`、标准 `marker_code/finding_code`、来源引用。
- `evidence_level`：`objective_lab`、`imaging_pathology`、`symptom_cluster`、`patient_reported`。
- `deviation_tier`：`T1`、`T2`、`P0` 或 `unknown`。
- `crosses_clinical_decision_line`。
- `trend`：`worsening`、`stable`、`improving`、`unknown`；只有同一标准指标、单位可比且存在至少两个明确检测日期时才判趋势。
- `objective_organ_damage`。
- `intervention_eligibility`：`eligible`、`referral_only`、`non_intervenable`，并保存排除原因。

不得使用上传顺序代替检测日期。若指标字典缺少 T1/T2 或临床决策线阈值，只能标为 `unknown` 并要求复核，不得自行猜阈值。

### 3.2 机制链对象

`MechanismChain`

- `chain_id`、`axis_id/axis_name`。
- 有序节点 `upstream -> intermediate -> downstream`。
- 每条边的 `mechanism_rule_id`、方向和证据引用。
- 客观支持集合及同向性校验结果。

`HubCandidate`

- 节点位置：上游/交汇点。
- 证据强度。
- 可干预性。
- 可受益的下游节点数。
- 排除原因、排序分解项和最终名次。

`CoreHealthPortraitDecision`

- 选中的 1–3 条机制链。
- 3–5 项可发布的靶器官损害信号（仅在有客观器质性证据时）。
- 选中的 1–2 个首月靶点。
- 3–6 个有序干预步骤及其生活方式/营养方案引用。
- 主轴、规则版本、输入快照哈希、校验结果和审计信息。

该决策对象建议存入 `RecommendationDraft` 的内部字段，使用默认值保持旧数据兼容；最终审核和 PDF 重建复用同一决策或在输入哈希变化时重新计算，避免多路径结果漂移。

## 4. 版本化机制与阈值规则

新增 `backend/app/data/health_axis_registry.json`，只收录医学团队审核过的节点和有向边。第一版覆盖文档指定的六类通路：

- 肠道屏障破坏 -> 内毒素/炎症负担 -> 肝脏代谢解毒超负荷（肠-肝轴）。
- 炎症负担 -> 内皮功能异常 -> 凝血/心血管风险（炎症-内皮-凝血轴）。
- 皮质醇/压力节律异常 -> 睡眠、免疫或代谢失衡（HPA 轴）。
- 甲状腺功能异常 -> 能量与糖脂代谢异常（甲状腺-代谢轴）。
- 肠道屏障/菌群异常 -> 黏膜免疫与全身炎症异常（肠-免疫轴）。
- 肠道异常 -> 神经递质/炎症信号 -> 睡眠与认知异常（肠-脑轴）。

每条规则必须声明：允许的标准指标/发现代码、方向、最少客观支持数、可作为枢纽的节点、不可干预节点、依赖顺序和患者可见命名。优先复用现有 `marker_dictionary.json`、`clinical_finding_dictionary.json`、`support_goal_catalog.json` 的标准代码，不用自然语言关键词直接决定因果关系。

扩展指标规则时增加经审核的 T1/T2、临床决策线和可比单位配置；影像/病理发现单独配置是否仅为损害信号或就医项。知识库中的“上游关联/下游影响”只能作为规则编制来源，不能在运行时未经审核直接生成因果边。

## 5. 判读与决策算法

### 5.1 数据分级

1. 将最终医生确认后的异常适配为 `GradedFinding`。
2. 按客观检验 > 影像/病理 > 症状群 > 自述标注证据等级。
3. 基于版本化阈值判 T1/T2/P0，并记录是否越过临床决策线。
4. 相同指标跨时点归一单位后判断趋势；恶化者在同证据等级内上调处理级别，但不能绕过红旗与不可干预筛除。

### 5.2 关联建链

1. 只从注册表允许的有向边构图。
2. 一条候选链必须同时通过：存在审核过的生理通路、方向与本病例异常方向一致、同链至少两项客观指标同向支持。慢性食物敏感不得单独成为链、上游根节点或唯一客观支持；只有存在另一项独立、非食物敏感的客观证据且机制规则匹配时，才可作为辅助证据。
3. 合并重复链并最多保留 3 条；没有合格链时输出“证据不足”三句回退模板，不把身体系统列表伪装成机制链。

### 5.3 枢纽选择

先过滤再排序：

1. 先把风险拆成 `P0_referral`、`review_required`、`dose_caution`。只有 P0 和 `referral_only/non_intervenable` 节点直接排除出营养靶点；它们仍进入安全警示、就医通道，符合客观器质性条件时也可进入第一句损害信号。孕哺、未成年、相互作用等非 P0 提示不得被误判为“停止生成报告”。
2. 优先多链交汇或更上游的可干预节点。
3. 再比较客观证据强度、可干预性和下游收益面。
4. T2/恶化趋势只作为合格枢纽之间的加权或平局项，不能把最严重的下游损害自动变成靶点。
5. 取 1–2 个靶点；只有一条合格主链时取 1 个。高龄、多重用药、虚弱或当前补充剂负荷较高时强制降为 1 个并标记低负荷起步。

排序必须输出分解项和排除原因，供医生端审计，不只保存一个不可解释的总分。

### 5.4 有序闭环

从靶点对应的生活方式协议、支持目标和最终推荐方案中选择 3–6 步，并建立显式依赖：

- 去除触发因素 -> 补充支持。
- 胃酸/基础消化 -> 杀菌清障 -> 菌群重建 -> 黏膜修复。
- 胆汁/排泄通道通畅 -> 肝脏解毒支持。
- 上游生态或节律修复 -> 下游器官支持。

每一步保存 `linked_lifestyle_action_ids`、`linked_support_need_ids` 或 `linked_sku_ids`。没有实际方案承接的步骤不得写进第一节。

## 6. 三句话渲染与校验

渲染器严格输出一个字符串、恰好三句话：

1. 第一句：1–3 条带方向的机制链交叉联动；如存在客观器质性证据，附 3–5 项可溯源损害信号。
2. 第二句：首月严格聚焦 1–2 个已通过枢纽算法的核心，不使用“等”留尾。
3. 第三句：按依赖顺序写 3–6 个动词短语，并以主链实际轴名的功能稳态目标收束。

新增前后两级校验：

- 决策校验：链数、边合法性、客观聚集、靶点资格、靶点数量、闭环依赖、方案承接、轴归属。
- 文本校验：三句、链名含方向、器质性信号来源、步骤数、禁词、无多余指标清单、末句轴名一致。

强制校验器必须是“报告内容安全闸门”，不能成为“报告生成熔断器”：

1. 第一次校验失败时，使用同一批已审核事实重新计算决策一次。
2. 决策有效但文本不合规时，不再次调用自由生成模型，改用确定性三句模板渲染。
3. 证据不足或无法形成合格机制链时，返回“资料不足—补充检查/记录—再评估”的合规三句模板。
4. 存在 P0 且没有任何合格营养靶点时，进入 `referral_only` 安全模式：第一句陈述可溯源风险信号，第二句聚焦医学评估与风险控制而不伪造营养靶点，第三句给出就医、资料准备和复核顺序；其他报告章节继续生成。
5. 任一回退均设置 `manual_review_required=true`、`portrait_status=degraded` 和结构化审计原因，但不得向上抛出导致整份报告、审核、PDF 或外部接口失败的异常。
6. 只有系统级不可恢复故障（例如存储失败）才允许终止流程；单个规则缺失、未知阈值、建链失败、文本校验失败都必须安全降级。

因此不得发布旧式不合规文本，也不得因为第一节失败而丢失整份报告。校验器应返回 `CorePortraitResult(text, status, violations, decision)`，由调用方始终取得可发布或需复核的第一节文本。

## 8. 测试与验收

### 8.1 单元测试

- 下游异常最严重，但上游节点满足四判据时，选择上游节点。
- P0、结节/占位、遗传易感和陈旧改变可作为损害/背景，不得成为靶点。
- 少于两项客观同向支持时，不得生成确定性机制链。
- 最多 3 条链、最多 2 个靶点、3–6 个步骤、恰好三句话。
- 检验值带数值和单位；症状/MSQ/自述不得进入器质性损害信号。
- 趋势只有日期和单位可比时才判定；恶化可上调处理但不能越过禁入规则。
- 高龄/多重用药/虚弱/补充剂负荷较高时只保留一个靶点。
- 末句轴名必须来自主链，禁止空泛“重要窗口期”“多系统需关注”。
- 对每一种校验失败注入故障，验证第一节进入合规回退、其他章节仍存在、审核接口成功返回且 PDF 可以生成。
- P0-only 场景验证进入 `referral_only` 安全模式，不产生营养靶点、不吞掉风险信号，也不中断报告生成。
- 慢性食物敏感单独存在时不得形成主线；与独立非食物敏感客观证据及审核机制边共同存在时，只能作为辅助证据。

### 8.2 场景测试

1. 截图型病例：肠道屏障破坏 -> 肝脏代谢解毒超负荷 -> 全身慢性炎症；ALT 等客观异常进入损害信号，肠道管理与肝脏代谢支持成为 1–2 个靶点，步骤按消化基础/清障/重建/屏障/肝脏支持排序。
2. 严重肾功能异常：先进入就医通道，不把“肾脏减负”作为营养干预枢纽。
3. 甲状腺或乳腺结节最高分：保留随访信息，但不能成为首月营养靶点。
4. 只有睡眠自述：不声称形成 HPA 因果链；使用资料不足回退文本。
5. 两条链共享肠道屏障或炎症节点：交汇节点优先于单条链上更严重的末端指标。

### 8.3 集成与回归

- 同一病例在草案、医生审核、重新生成、PDF 和外部报告中的第一节完全一致。
- 医生修订异常后输入哈希变化，第一节重新计算；未变化时不得漂移。
- PR #31 的当前补充剂增删改和重复提醒继续工作，且客户报告不泄露医生端提示。
- 运行 `test_report_content.py`、`test_case_analysis.py`、`test_recommendation.py`、`test_pdf_export.py`、`test_remote_rag_fusion.py` 和外部接口回归。
- 更新旧测试中“五条主线”“系统首项即枢纽”“重要窗口期”等与新规则冲突的断言。

## 9. 建议实施顺序

1. 以当前本地跟踪分支 `codex/current-supplement-overlap`（PR #31 head）作为实现基线，不合并 `main`。
2. 建立版本化阈值/机制注册表与领域模型，同时补注册表完整性测试。
3. 实现判读层和决策层，先产出可审计结构，不生成患者文案。
4. 实现三句渲染与强制校验器，替换旧 `build_core_health_portrait()`。
5. 统一草案、审核、PDF、外部接口的数据流，并从 RAG 改写范围排除第一节。
6. 补齐单元、场景、集成和 PDF 视觉回归；使用至少一组医学团队金标准病例做盲评。
7. 更新规则版本与缓存版本，小流量启用，对“回退率、人工改写率、错误建链率、红旗误入靶点率”做上线监控。

## 10. 完成标准

- 第一节所有输出通过 R1–R7 和六项校验器。
- 任何靶点均可追溯到四判据评分和排除过程。
- 任何机制边均来自审核过的注册表，并有至少两项同向客观证据支持整条链。
- 严重程度不再是首要选择条件；红旗和不可干预发现的靶点误入率为 0。
- 截图型目标表达可稳定生成，同时不牺牲医学安全、证据可追溯性和多路径一致性。
