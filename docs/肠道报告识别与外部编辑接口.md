# 肠道报告识别、剂量治理与外部编辑接口说明

本文档说明三类专用报告识别、营养素剂量治理、外部解析校对和待审草案编辑能力。所有接口均遵循既有安全边界：产品目录、禁忌、医生规则和人工审核优先；RAG 只增强解释，不负责选品或覆盖安全结论。

## 1. 医生操作流程

1. 甲方系统使用系统间签名换取医生 Bearer Token。
2. 创建病例并上传病例报告、专用报告和问卷。
3. 读取解析结果，人工校对指标、单位、参考范围和专用报告字段。
4. 保存解析校对；只有已校对结果可以进入推荐上下文。
5. 生成待审营养素草案。
6. 医生调整产品顺序、剂量和理由；服务端重新执行目录、禁忌和病例安全校验。
7. 内部工作台完成最终审核发布和 PDF 导出。

外部接口不提供审核发布能力，甲方医生不能绕过内部工作台直接发布最终报告。

## 2. 专用报告识别

### 2.1 慢性食物敏感

结构化字段：

| 字段 | 含义 |
| --- | --- |
| `mild_foods` | 轻度反应食物 |
| `moderate_foods` | 中度反应食物 |
| `high_foods` | 重度反应食物 |
| `interpretations` | 原报告固定解读 |

安全规则：

- 结果只用于阶段性饮食观察和草案展示。
- 不等同于 IgE 介导的食物过敏诊断。
- 不会仅凭慢敏结果触发营养素产品推荐。
- 长期回避或重新引入需由医生确认。

### 2.2 肠道功能健康评估

支持的核心指标：

| `code` | 中文名称 | 常见单位 |
| --- | --- | --- |
| `anti_gliadin_siga` | 麦胶蛋白抗体 | `U/L` |
| `anti_httg_siga` | 组织转麸胺酶抗体 | `U/L` |
| `secretory_iga` | 分泌型免疫球蛋白 sIgA | `ug/mL` |
| `fecal_calprotectin` | 粪便钙卫蛋白 | `ug/g` 或等值 `mg/kg` |
| `zonulin` | 解连蛋白 Zonulin | `ng/mL` |
| `beta_glucuronidase` | β-葡萄糖醛酸酶 | `U/g` |
| `pancreatic_elastase` | 胰弹性蛋白酶 | `ug/g` |

报告自身参考范围优先。字段缺失、错位或无法确认时保留为空并标记人工复核，不从说明文字猜测患者数值。

粪便钙卫蛋白高于报告参考范围时，系统优先生成临床复核和及时就医提示，不能仅据此升级营养素方案。

### 2.3 肠道菌群

只提取关键总结，不导入全部菌属明细：

- 健康评分、多样性指数及报告参考范围。
- 检测菌属数量、优势菌属、稳定性、多样性判断和肠型。
- 异常/偏高菌属、不足有益菌属。
- 风险分类、重点风险、营养影响和报告总结。

菌群疾病风险属于弱背景证据，只能用于饮食多样性、膳食纤维耐受、排便和生活方式分析，不能单独选择 SKU。

### 2.4 识别策略

- PDF 文本层和布局文本优先，现有 OCR 作为兜底。
- 使用多重标题锚点识别模板，避免把目录页误判为结果页。
- 每次自动识别后统一设置 `needs_manual_review=true`。
- 医生保存校对后，服务端设置 `review_status=reviewed` 并重建摘要行。
- 最终 PDF 不显示报告页码、教材来源或内部证据 ID。

本轮未重建 `rag_corpus.jsonl`、`index.faiss` 或 `metadata.pkl`。专用指标只扩展本地查询词和运行时上下文。

## 3. 剂量治理

### 3.1 派生文件

- `backend/app/data/product_dosage_matrix.json`：产品剂量候选矩阵。
- `backend/app/data/product_dosage_import_report.json`：映射、冲突、缺失和禁用产品报告。
- `scripts/import_product_dosages.py`：本地 Excel 导入脚本。

原始 Excel 不进入 Git。导入命令：

```powershell
python scripts/import_product_dosages.py "D:\受控目录\产品服用方式.xlsx"
```

### 3.2 生效优先级

```text
医生本次病例修改 > review_status=reviewed 的剂量矩阵 > 产品目录 dosage_rule
```

当前新矩阵整体状态为 `pending_manual_review`，所有 Excel 剂量均为候选，不会自动覆盖产品目录。逐项审核后，才可把对应条目的 `review_status` 改为 `reviewed`。

### 3.3 安全规则

- 自动草案只使用已审核的保守基础剂量。
- 强化、急性、儿童、备孕、术后等场景只保存在 `doctor_only_options`。
- 空白剂量不推断，继续使用产品目录兜底并提示待确认。
- 序号 25 综合消化酶、序号 26 复合益生菌保持禁用。
- DHEA、高剂量维生素 D3、女性激素平衡类不进入自动草案，只能由医生逐例明确加入。
- 已移除鱼油、甘氨酸镁、甲状腺支持等产品的首月高剂量硬编码。

## 4. 解析校对接口

### 4.1 读取解析校对

```http
GET /api/v1/cases/{case_id}/parsing-review
Authorization: Bearer <token>
```

响应核心字段：

| 字段 | 含义 |
| --- | --- |
| `revision` | 当前解析版本 |
| `review_completed` | 是否已完成人工校对 |
| `files` | 文件解析状态、校对文本和缺失项 |
| `normalized_lab_items` | 标准化实验室指标 |
| `specialty_reports` | 三类专用报告结构化结果 |
| `missing_fields` | 病例级缺失项 |
| `editable_fields` | 允许修改的字段说明 |

### 4.2 保存解析校对

```http
PUT /api/v1/cases/{case_id}/parsing-review
Authorization: Bearer <token>
Content-Type: application/json
```

请求示例：

```json
{
  "expected_revision": 2,
  "files": [],
  "normalized_lab_items": [],
  "specialty_reports": [],
  "missing_fields": [],
  "review_notes": "已核对"
}
```

医生身份从 Bearer Token 获取，客户端不能提交 `reviewer_id`。服务端重新校验：

- 每个文件必须属于当前病例，且每个附件恰好提交一次。
- `marker_code` 必须存在于指标字典。
- 数值必须有限，参考下限不能高于上限。
- 标准化单位必须符合指标字典。
- 专用报告和其中每个指标的 `file_id` 必须属于当前病例。
- 专用报告 ID、报告类型、来源文件和肠道指标代码集合必须与自动解析结果一致；外部客户端只能校正字段值，不能凭空新增报告或指标类型。

## 5. 待审营养素草案接口

### 5.1 读取草案

```http
GET /api/v1/drafts/{draft_id}/nutrition-recommendations
Authorization: Bearer <token>
```

现有 `GET /api/v1/cases/{case_id}/nutrition-recommendations/latest` 同样返回：

- `revision`
- `editable_fields`
- `recommendations`
- `contraindications`
- `missing_info`

### 5.2 修改草案

```http
PATCH /api/v1/drafts/{draft_id}/nutrition-recommendations
Authorization: Bearer <token>
Content-Type: application/json
```

请求示例：

```json
{
  "expected_revision": 1,
  "recommendations": [
    {
      "sku_id": "sku_example",
      "dosage": "每日 1 粒，随餐服用。",
      "reason": "医生结合已校对指标、用药和耐受情况后保留。"
    }
  ],
  "edit_reason": "调整顺序与基础剂量"
}
```

数组顺序即产品展示顺序；省略某个原有产品即删除。可以添加已启用目录产品，但服务端会重新执行产品目录、禁忌和病例安全校验。

客户端不能提交 `warnings`、`contraindications`、`evidence_ids` 或 `evidence_details`。这些字段由服务端重新生成或保留，额外字段会返回 `422`。

已发布草案、拒答草案和存在审核决定的草案禁止修改。最终发布仍由内部工作台完成。

## 6. 版本冲突与错误码

| HTTP 状态 | `detail` 示例 | 说明 |
| --- | --- | --- |
| `401` | `Invalid or expired bearer token` | Token 无效或过期 |
| `403` | `Case is not owned...` | 医生无病例或草案所有权 |
| `404` | `Draft not found` | 病例、草案或资源不存在 |
| `409` | `parsing_revision_conflict` | 解析校对版本过期 |
| `409` | `draft_revision_conflict` | 草案编辑版本过期 |
| `409` | `draft_not_editable` | 草案已发布、拒答或不可编辑 |
| `422` | `Unknown marker_code` | 指标代码不在字典中 |
| `422` | `product_not_found_or_disabled` | 产品不存在或未启用 |
| `422` | `product_contraindicated` | 病例命中产品禁忌 |
| `422` | `invalid_dosage` | 剂量为空、过长或包含不允许的用药指令 |

客户端收到 `409` 后必须重新读取最新资源及 `revision`，让医生确认差异后再提交，不得静默覆盖。

## 7. Postman 验证

使用：

- `postman/external_api.postman_collection.json`
- `postman/external_api.local.postman_environment.json`
- `postman/fixtures/labs.txt`

集合按 10 步执行完整流程，并验证解析版本递增、草案版本递增以及未审核报告下载返回 `409`。安全字段篡改、非法 SKU、禁忌冲突和过期版本由后端单元测试覆盖。

```powershell
npx --yes newman run postman/external_api.postman_collection.json `
  -e postman/external_api.local.postman_environment.json `
  --working-dir .
```

环境中的 `shared_secret` 仅用于本地测试。生产环境必须通过安全渠道配置，不得写入仓库或 Postman 交付文件。

## 8. 隐私与审计

- 原始病例、PDF、DOCX、XLSX、上传文件和本地数据库不进入 Git。
- 真实病例验证不向外部评测模型发送，不在日志输出患者姓名、样本号或原文。
- 解析校对审计只记录数量、版本和是否有备注。
- 草案编辑审计只记录新增/删除 SKU、顺序变化、剂量发生变化的 SKU 和版本，不记录原始病例正文。
